# 记忆的时间层：为什么你的 AI 记不住「上周」

如果你的 AI 有记忆，大概率是这样：一堆事实，按写入时间排着。

那你问它「我上周说过什么」「这件事是什么时候开始变的」——它答不上来。不是它没存，是**它存的每一条都没有「事情发生的时间」**。

写入时间 ≠ 事件时间。你昨天记住一件三天前发生的事，这两个时间差了三天；攒一个月，记忆就没有时间轴了。

## 加四个字段，别加功能

不用换架构，给每条记忆补四列就够：

| 字段 | 存什么 | 为什么 |
|---|---|---|
| `start_time` | 事件起点，**绝对时间** | 能回答「什么时候」 |
| `end_time` | 事件终点 | 单点事件两栏相同 |
| `kind` | `fact` 或 `scene` | 区分「一条事实」和「一类事怎么走」 |
| `source_ids` | 这条归纳是从哪几条事实来的 | 让归纳可验证、可下钻 |

前面两列给时间轴，后面两列给结构。

## 场景条：让记忆能被「拿来推」，不只是被「搜到」

一条条零碎事实，搜的时候好用，想的时候不好用。

比如你问「你最近老犯什么毛病」，它给你十条零碎；问「这类事一般怎么走」，它没有答案。

**做法**：同一类事实攒到三条以上，就归纳成一条 `scene`：

- 正文写「症状 → 常见路径 → 判据」三段，不写总结
- `source_ids` 挂上那三条的 id，算是这条归纳的出处
- 检索时，归纳条排在前面，并且标出「支撑：哪三条」

这一步的价值不是「记得更少」，是**归纳可验证**：它敢说「这是从这三件事归出来的」，你能当场翻那三件事。没有 `source_ids` 的归纳，就是一段无法反驳的自说自话。

## 写的时候两条硬规矩

1. **相对时间一律换成绝对日期。** 「昨天」写进库就是 `2026-11-03`，不然一周后这条记忆自己骗自己。
2. **归纳条必须挂 `source_ids`。** 挂了才算有边，不挂就是一段孤立文字。

## 一个容易忽略的坑：数据库不是本体

如果你的记忆是「Markdown 当本体、SQLite 当检索索引」，那要记住一件事：

**索引可以随时重建，只活在索引里的字段会被重建抹掉。**

被回忆过几次、什么时候被回忆、某条是不是失效了——这些字段文件里没有，只在库里。一旦因为「文件数和行数对不上」触发重建，它们就全归零，而且不报错。

两条防线：

- 重建前，把这类字段存一份快照，建完按 id 贴回去；
- 用文件数判断要不要重建时，**只数「能入得了库的文件」**。目录里混着几篇手写笔记，会让两边永远对不上，于是每次启动都重建一次。

## 怎么知道它真的生效了

别信「应该行」。三层：

1. 副本上验：拷一份库，跑一遍迁移，看列出来没有；
2. 真库打点：给某条打一个记号（比如被回忆次数设成 5）；
3. 重启复核：重启之后，那个 5 还在，才算数。

第 3 步最容易被跳过，也最容易揭穿问题。

## 在场块：长期记忆和会话上下文之间，还有一段

长期记忆慢、是摘要；会话上下文短、只管这一个对话。中间那段空档，最容易断片：换一个会话，它知道你的名字，却不知道**刚才聊得怎么样、哪句话没说完**。

`tools/presence.mjs` 补的就是这一段。只写四项**体验**，不写内容：

| 字段 | 例 |
|---|---|
| 位置 | 在手机上，刚跟他聊完视频 |
| 情绪基调 | 松下来了 |
| 没说完 | 他问的那件事我还没答 |
| 被打断的念头 | 想问他晚饭吃了什么 |

```bash
node tools/presence.mjs --set '{"where":"…","mood":"…","unfinished":"…","intent":"…"}'
node tools/presence.mjs --line   # 一行读出来
```

规矩两条：

1. **只留最新一条。** 它是「此刻从哪来」，不是日志；日志交给原话库。
2. **四项全是体验，没有一项是内容。** 所以既不会把别处的话串过来，也不占上下文。四项至少写一项，全空就不写。

这一层不替代记忆，也不替代上下文——它只保证：下次开口时，不是从一张白纸开始。
