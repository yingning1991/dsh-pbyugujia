# 改完了，怎么算验过了

一个下午，同一个毛病犯了三次——不是知识不够，是**改完没验**。

三次是这样的：

1. 一个数字改了文件名，改完打开**另一个文件**，同一句话还写着旧数字；
2. 自己写的检查脚本，号称「看全部」，实际十二条里只给出三条；
3. 写新脚本时直接覆盖了一个**早就存在**的同名工具——它就在工具表里登记着，一眼没看。

三次都是同一个动作：**只检查了自己正要改的那一点，没检查它旁边。**

## 两条标准

- **核得准 = 跑得通。** 不是「看着对」，是真跑过、真看到结果。
- **做得准 = 不返工。** 不是「这一处改了」，是「它旁边没有旧说法」。

## 收尾五问

改完任何东西，问这五句，不用工具也能问：

**1. 它旁边还有旧说法吗？**
同一句话常写在你没打开的那个文件里。改完拿关键串全文搜一遍，别只信你改的那处。

**2. 这个「全部」真的是全部吗？**
凡 `--all`、全量、完整，拿总数对输出行数。数字对不上，多半是分类有盲区——比如「七天内」和「已过期」两桶之外，还有一大片没归类的。

**3. 我是在「看着对」还是在「跑通过」？**
三层验收：副本上验 → 真库打点 → 重启复核。只做完第一层就宣布验完，是假验收。

**4. 这个数字正常吗？**
统计值异常地一致（永远是 0、永远不变），先怀疑**采集**，别急着解释成事实。数据全 0 的时候，最容易得出的结论是「这件事没发生过」——而真相往往是「记录它的那段代码坏了」。

**5. 我一次改了几层？**
同时改两样，验不通就分不清是谁的错。一次改一层，验过再动下一层。

## 写文件前还有一句

`ls` 一下目标目录，`grep` 一下工具表，看这个名字有没有被占用。

覆盖类命令（`cat >`、重定向写）**不会问你**，它绕过「没读过的文件不许改」那层保护。新建用它可以，改已有文件要用心跳一下。

## 最后：把这两条做成脚本

人不会每次都记得问五句。所以把**不变量**写成代码，每次改完跑一次：

- 定时任务条数对不对
- 新加的字段时间在不在
- 文档里声称的数字跟实际对不对
- 「全部」开关的输出条数等于总数吗
- 引用的文件真的存在吗（不然跑起来才 ENOENT）

脚本不需要聪明，只需要**每次都会跑**。

> 一个系统最可信的时刻，不是它不出错，是它能在同一个地方错到第三次，然后被自己抓住。

## 声称体检：说的「完成」，有没有证据

「跑通了」「改好了」「已落地」——这些话最容易滑。滑不是因为撒谎，是因为**只改了字也算改**、**上一轮跑过这次没跑也算跑过**。

`tools/claim-audit.mjs` 把这件事变成能跑的检查。它只读 `chat.db`，零模型调用：

```bash
node tools/claim-audit.mjs        # 今天
node tools/claim-audit.mjs 7      # 最近 7 天
node tools/claim-audit.mjs 1 --list   # 每条都列出来
node tools/claim-audit.mjs 1 --line   # 一行，挂每日复盘
```

判据：

- **强声称**（已落地 / 已上线 / 已验证 / 全绿 / 修好了）→ 这一轮（上次你发言之后）要有 `bash/shell`，或者确实排进了定时；只有 `edit/write` 算「只改字」，什么都没有算「空口」。
- **动作声称**（已改 / 已写 / 已建 / 已挂）→ 至少有写或动作，否则「空口」。
- **同一工具重复只算一次证据**：同一条命令绿两次，不是两条独立证据。
- **复述不算新声称**：同一会话里已经证实过的「全绿」，后面再提只当复述。

边界要说清：它只能查「有没有跑」，查不出「跑得对不对」；跨轮的总结（这一轮只是在回答你上一轮问的事）会被判「待核」，这属于正常误报，人工看一眼即可。宁可多报一条，不要漏掉真没跑的那条。
